# AnimalRegistered Event

## Overview

The Animal Registration Service publishes an `AnimalRegistered` event whenever a new animal is registered.

Events are sent through RabbitMQ and consumed by the Traceability Service, which stores the animal's registration number in its own database.

This allows the services to communicate asynchronously without depending on each other being available at the same time.

## Event Structure

```json
{
  "eventId": "3f55d2aa-7dbc-4d88-9ac7-fbcbb20895d6",
  "eventType": "AnimalRegistered",
  "occurredAt": "2026-10-17T12:00:00Z",
  "registrationNumber": "DK-2026-RABBIT001"
}
```

| Field | Description |
|---|---|
| `eventId` | Unique identifier used to detect duplicate events |
| `eventType` | Identifies the event as `AnimalRegistered` |
| `occurredAt` | Timestamp indicating when the event was created, in UTC |
| `registrationNumber` | Registration number generated by the Animal Registration Service |

## RabbitMQ Configuration

| Setting | Value |
|---|---|
| Exchange | `slaughterhouse.events` |
| Exchange type | `topic` |
| Routing key | `animal.registered` |
| Queue | `traceability.animal-registered` |
| Message format | JSON |

The exchange routes events to the Traceability queue using the routing key.

## Transactional Outbox

When an animal is registered, the Animal Registration Service saves both the animal and an outbox event in the same PostgreSQL transaction.

A scheduled publisher checks for unpublished events every five seconds after the previous execution finishes.

For each pending event, the publisher:

1. Serializes the event to JSON.
2. Publishes it to RabbitMQ.
3. Waits for a publisher confirmation.
4. Marks the event as published if RabbitMQ acknowledges it.

If RabbitMQ is unavailable, the event remains unpublished and is retried during a later execution.

This allows animal registration to continue while the message broker is unavailable, provided the local database is accessible.

## Event Consumption

The Traceability Service listens to the `traceability.animal-registered` queue.

When an event is received, the consumer inserts the animal's registration number into the `animal` table and records the event ID in `processed_event`.

Both inserts are performed in a single database transaction.

The event ID is used to detect duplicate deliveries. If an event has already been processed, the consumer skips the database changes and acknowledges the message.

Malformed events are rejected without requeueing. Database failures cause the message to be requeued for another attempt.

## Limitations

The current implementation uses manually configured RabbitMQ exchanges and queues.

Publisher confirmations indicate that RabbitMQ has accepted a publication, but do not independently guarantee that a message was routed to a queue.

Repeated database failures may also cause repeated delivery attempts. More advanced retry handling and dead-letter queues are not implemented.
